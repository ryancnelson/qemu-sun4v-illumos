How the Niagara appliance's OpenBoot defaults are edited
========================================================

The file beside this note is named nvram1, but this appliance's effective
boot-device, boot-file, and auto-boot? values do not come from that file.

At startup, this Niagara OpenBoot executes "Update NVRAM with PD data".  It
loads matching properties from the "variables" node in md.bin after reading
the NVRAM token store.  The accepted machine-description source contains:

  boot-device = "vdisk";
  auto-boot? = "false";

Those platform-description values explain why hand-edited, CRC-valid nvram1
records still read back as vdisk and false.  QEMU's nvram-file option is not
the problem: it maps the requested 8192-byte file directly and does not load a
second firmware-directory nvram1 over it.

For this release, do not binary-edit nvram1.  Woodpecker runs:

  scripts/prepare-release-firmware.sh

That procedure:

1. verifies the SHA-256 of Oracle's OpenSPARC T1 Architecture 1.5 archive;
2. builds Sun's mdgen on x86-64 using the repository's endian-correctness
   patch;
3. verifies the accepted two-CPU 2c8t_guest.pp.bak and regenerates the baseline
   md.bin with SHA-256 e5d0dfa0cef98daef762ed48a19ace9c372e4bc46342bc03200eb1cf219379ac;
4. derives a release source with:

     boot-device = "/virtual-devices@100/disk@5:a";
     boot-file = "-v";
     auto-boot? = "true";

5. compiles and installs the derived md.bin and the pinned two-CPU hv.bin into
   the firmware set;
6. packages it, starts a fresh QEMU, and requires an untouched cold boot to
   reach the OpenIndiana login prompt.

The procedure prints and records the derived release md.bin SHA-256. The input
source hash, byte-identical baseline build, and exact source transformation are
the fail-closed checks; the derived hash is not copied from an earlier build.

The byte-identical baseline is also packaged as md.bin.manual. Setting
OPENBOOT_AUTO_BOOT=false explicitly selects that manual/debug policy for the
short interactive-console transport test. The release and normal first-boot
paths never select it.

The release boot-file deliberately omits -k so kmdb is not loaded during a
normal boot. Set OPENBOOT_AUTO_BOOT=false on docker run to select the baseline
machine description and stop at the OpenBoot ok prompt; removing or renaming
nvram1 is not a supported policy mechanism.

The source transformer refuses an unknown input hash or duplicate/missing
properties.  The cold-boot gate is the final authority.  A build that reaches
the OpenBoot ok prompt or requires a typed boot command must not be released.

Authoritative format evidence is in the OpenSPARC source:

  obp/obp/arch/sun4v/niagara/loadconfig.fth

Its pdnvupdate word copies the platform-description "variables" properties
into OpenBoot's options dictionary during stand-init.
