01 / 05

Try it before reading any of this.

OpenIndiana Hipster 2025.12 on SPARC64, published for both amd64 and arm64. No OpenBoot commands, no disk images to fetch, no assets to mount.

HOST SHELL

$ docker run --pull always --rm -it \

  --name openindiana-sparc64 --hostname oi-basecamp \

  --memory 6g --cpus 2 \

  --cap-add NET_ADMIN --device /dev/ppp --sysctl net.ipv4.ip_forward=1 \

  --tmpfs /run/unit100:rw,size=1200m,mode=0700 \

  ghcr.io/ryancnelson/sparc64-qemu-openindiana-20g@sha256:ce577fba08479d47c960427ebb39dd802473345feee28c83cd8c31eab93c4a7b

This is a disposable first run: it creates a fresh anonymous guest-state volume, then --rm removes that state with the container. --pull always refreshes the convenience alias before starting. This page is pinned to the multi-architecture manifest shown above. Log in as root / root; that is a public lab-only credential. Then be patient: emulated SPARC is slow, and how slow depends on your host. About seven minutes to a login prompt on a bare-metal Linux builder; closer to forty under nested virtualization like Docker Desktop on a Mac. Verbose device messages keep scrolling after the prompt appears — that is normal, and it fooled me once already.

Want a persistent workspace? Use a newly created named volume with one immutable release tag or digest. That volume holds the writable guest disk extracted on its first start. Pulling a newer image does not upgrade it; use a new volume for a new release, and do not delete an existing one unless its guest state is disposable.

03 / 05

Three problems stood between a running lab and a shippable thing.

The machine wouldn't boot itself

Every boot needed a human to type an OpenBoot command. The obvious fix — set boot-device and auto-boot? in NVRAM — does not work on this machine, and it took building the feature to find out why. I added a real -M niagara,nvram-file=PATH property to QEMU, mapped the file shared, and proved with a firmware canary that OpenBoot never writes it: variable updates are routed through an LDOM Domain Service provider that doesn't exist here, so it prints Unable to update LDOM Variable and moves on. QEMU's generic -prom-env is ignored for the same reason.

The answer was one layer down. Niagara's OpenBoot runs pdnvupdate at stand-init and copies boot policy out of the Machine Description's variables node — which overrides the token store regardless of what you put there. So the release rebuilds Sun's own mdgen, reproduces the accepted MD byte-for-byte as a gate, and only then derives one with the boot path, arguments, and auto-boot flag baked in. A negative test proved it: firmware with no disks attached still printed Boot device: /virtual-devices@100/disk@5:a and tried, unattended.

The disk had to stay exactly where it was born

The 20 GiB root boots as unit105 and only unit105. Move it to the conventional unit104 and ZFS can't find its label by path, falls back to a full device scan, and the scan hands hsimd a 666 KiB request. The driver asserts sz <= 128*1024 and the kernel panics. ZFS aggregates vdev I/O up to 1 MiB and calls ldi_strategy() without consulting the dki_maxtransfer the driver advertises. That is a real driver bug with a known fix, and it is not fixed yet — so the appliance documents the constraint instead of pretending it chose unit105 on purpose.

Two agreeing sides, silent anyway

The container's BBS answered nothing for four straight CI runs. Two plausible causes were wrong: a modem timeout (removed it; still silent) and a channel-readiness race (real, fixed, still silent). The decisive evidence was making the guest daemons print their own addressing:

PIPELINE 24 · BOUNDARY TRACE

guest-chand: ch0 ... dev /dev/rdsk/c1d0s2 base blk 640

guest-chand: ch1 ... dev /dev/rdsk/c1d0s2 base blk 2688

host default offset: 520093696 = blk 1015808 ← inherited from an older image

Both sides were healthy and framing correctly, into different parts of the disk. The container had inherited a byte offset from a previous project generation. Correct value: block 640, or 327680 bytes. Nothing about the protocol changed.

04 / 05

What's underneath.

The emulator is no longer mine alone. Masayuki Murayama published an extensively extended QEMU sun4v machine — MMU, traps, interrupts, eight disks, async I/O, SMP — and rather than race it, this project now builds on it. That was the original stated goal of the first page, and it's done.

01Any amd64 or arm64 Linux Docker host including Docker Desktop on Apple silicon, slowly
02QEMU 10.2 · Murayama sun4v + persistent NVRAM + TLB range flush compiled inside the image from a pinned source archive
03OpenSPARC hypervisor + OpenBoot + derived Machine Description the MD is what makes it boot unattended
04OpenIndiana Hipster 2025.12 · sun4v · ZFS root on unit105 distpool, scrubbed clean, user jack present

Bringing his fork up on a Tribblix host also surfaced a machine-initialization bug worth knowing about: niagara_init() probes only unit 100 (or 102) before it will initialize the vdisk backend at all. A perfectly good disk at unit 104, by itself, never reaches the scan and looks broken to the firmware. A small carrier image at unit 100 wakes it up — which is why the appliance ships one.

Dmitry Pimenov has been attacking the same machine from below, rebuilding the OpenSPARC hypervisor with its Fire/PCIe path live and getting QEMU's e1000 to appear in the OpenBoot device tree. His work and this project's guest/installer side are complements, and his virtual-disk size fix is already upstream in QEMU.

05 / 05

What is honestly still broken.

The point of the first page was that each result reduced the problem instead of disguising it. Same rule here. These are the things I would not want somebody to discover on their own after trusting the paragraphs above.

01You can't rebuild my binary from GitHub The image pins QEMU commit 049affb2, which exists only in a working checkout and the pinned tarball. Publishing it is the top of the list.
02The root is welded to unit105 Because of the hsimd large-I/O assertion above. The driver fix is diagnosed, not written.
03There is no Ethernet The guest has real IP, but over PPP on a shared-disk channel plus container NAT. Framed Ethernet on channel 2 is designed and unimplemented.
04SSH is present but off, and there is no compiler The appliance boots to a console and starts networking from an explicit script, so sshd is installed but not running by default — bring the network up first, then enable the service. No compiler ships either; once the guest is online, pkg install developer-illumos-gcc works. Neither path is part of the release acceptance contract, so neither is exercised by CI.
05The installer recipe needs to be replayable This root began as an OpenIndiana installation booted from hSIMD-enabled derivative media; stock installer media lacks the driver. Post-install transformation and CI packaging made the release. The missing work is a published, current replay of that installer recipe and its hSIMD large-I/O gate—not proof that an installer cannot use hSIMD.
06A named root volume does not auto-upgrade It is guest state, extracted on first start. Pulling a newer image leaves that disk intact; use a new volume when changing releases until an explicit migration exists.
07The TLB patch is unproven Profiling says per-page TLB invalidation dominates boot, and the range-flush patch ships — but its controlled A/B has never been run. It is not a claimed speedup.

One smaller correction, since the first page leaned on the number: DTrace probe counts are per-image, not a property of the project. The August basecamp guest reported 82,806. The Basecamp R0 live media asserts exactly 72,893. This shipped appliance reports 77,745. All three are real; none of them are interchangeable.

EVIDENCE AND SCOPE

Every factual claim on this page traces to the repository or to a live check run on 2026-09-03: the boot transcript and probe count came from pulling the published :latest on arm64 Docker Desktop and logging in; the multiarch manifest was read from GHCR; the MD/NVRAM findings, channel offset, and hsimd assertion are recorded in the appliance experiment notebook and notes/. Not verified here: build times on other hosts, and anything about Murayama's or Pimenov's stacks beyond what they published and what this project reproduced.

The launch example is deliberately disposable. A named Docker volume is a persistent guest disk, not a cache: do not reuse it across image releases unless you intend to preserve that exact guest state. The live status page is operational telemetry, not a release certificate; the image identity and CI evidence are the release record.
