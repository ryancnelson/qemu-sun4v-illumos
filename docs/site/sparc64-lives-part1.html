PART ONE · EXPERIMENT LOG · AUGUST 19–24, 2026

Booting modern illumos on QEMU sun4v.

This is the record of the first five days: a Tribblix RAM-root boot, a Solaris 10 storage driver carried forward into modern illumos, an OpenIndiana live environment, and a PPP link built over a shared-disk channel. It records the working path and the mistakes that narrowed it.

Read the experiment log Continue to the packaged appliance
SCOPE

A live experiment, not yet a release.

The August work established that contemporary illumos kernels could run on the older QEMU Niagara machine and could use its unusual storage path. The OpenIndiana result described here was a long-lived live environment assembled from derivative media and repaired while it ran.

The installed ZFS root, QEMU 10.2 runtime, automatic boot, multi-architecture OCI image, and CI gates came later. Those belong to Part Two.

01 / EXPERIMENT LOG

What happened, in order.

The sequence matters. Several later steps only made sense after an earlier assumption failed.

AUG 19
TRIBBLIX

A boot archive was enough to start modern illumos.

Tribblix m34 loaded from its RAM-root archive. Disabling the Niagara performance-counter path with set cu_flags=0 avoided the measured PCBE panic. The guest eventually reached a login prompt despite slow service startup and several misleading pauses.

RESULT · BOOT DID NOT REQUIRE HSIMD
AUG 20
STORAGE

The Solaris 10 hsimd module loaded under Tribblix.

A working Solaris 10 guest served as the donor and behavioral reference. Its SPARC V9 module used kernel interfaces still available in Tribblix. After selecting an unused major number and registering the driver precisely, hsimd0 attached to /virtual-devices@100/disk@0.

RESULT · ALIGNED NONZERO READS AND WRITES VERIFIED
AUG 20–21
ARCHIVE

The change became a reproducible media edit.

Typing a binary into a live RAM root proved the idea but was not a workable boot process. The Tribblix boot archive was identified as a fixed-size UFS filesystem inside the ISO, mounted on a Solaris-family host, changed, checked, and written back into a protected copy. Readback checks caught a driver-registration quoting error before it became the procedure.

RESULT · REMASTERED ISO BOOTED AND ATTACHED HSIMD
AUG 21
IOCTL

A filesystem error exposed a driver contract bug.

HSFS initially reported corrupt media. The bytes were sound. The old driver returned success for the unsupported CDROMREADOFFSET ioctl without initializing its output, so HSFS used garbage as an offset. Returning ENOTTY let HSFS take its normal fallback path.

RESULT · MEDIA MOUNTED AFTER A NARROW HSIMD FIX
AUG 23
OPENINDIANA

An hsimd-enabled OpenIndiana image reached its live userland.

The same measured PCBE workaround, corrected hsimd module, and driver registration were added to a derivative OpenIndiana SPARC boot archive. OpenBoot loaded the image; after the kernel took control, the bytes appeared as an ordinary hsimd disk, not a CD-ROM. The guest mounted the HSFS media and its compressed solaris.zlib userland.

RESULT · OPENINDIANA 2025.12 RUNNING ON SUN4V
AUG 24
CHANNELS

The shared disk carried a console and a network.

Reserved blocks on the hsimd device already supported framed host/guest mailboxes. Channel 0 became a PPP byte stream to Linux; channel 1 became a separate root PTY where Ctrl-C interrupted the guest command instead of QEMU. The guest reached DNS and the Internet, mounted NFS, reached a Linux iSCSI target, and created and exported a ZFS pool.

RESULT · PPP, NFS, ISCSI, ZFS, AND SAFE CONSOLE OBSERVED
02 / DATA PATH

The “network interface” was a controlled use of shared storage.

QEMU and the guest exchanged framed bytes through a reserved area of the hsimd backing object. That transport was sufficient for PPP and a maintenance console. It did not turn the virtual disk into an Ethernet controller.

03 / CLAIMS AND LIMITS

What this experiment established.

BOOT

Tribblix and OpenIndiana sun4v kernels ran on the older QEMU Niagara stack from modified boot media.

STORAGE

A Solaris 10 hsimd module attached under modern illumos; exact-offset canaries verified its basic data path.

FILESYSTEMS

Correcting unsupported-ioctl behavior allowed HSFS media to mount. UFS boot archives could be edited and checked on a compatible host.

CHANNELS

Independent framed streams carried PPP and a safer maintenance console through reserved disk blocks.

NETWORK SERVICES

The live OpenIndiana guest demonstrated outbound IP and DNS, NFS, iSCSI, and a ZFS pool over the iSCSI path.

OBSERVABILITY

The captured first OpenIndiana guest exposed 82,806 DTrace probes. That number belongs to that guest, not every later image.

NOT YET PROVEN

This session did not produce the current installed ZFS-root appliance, a clean-room installer recipe, native Ethernet, or a general-purpose hsimd driver.

INSTALLER LINEAGE

The later root did originate through OpenIndiana’s installer after booting hsimd-enabled derivative media. It was not simply assembled without an installation.

DRIVER PROVENANCE

The original binary came from a Solaris 10 image. The hsimd source is now vendored and pinned, but exact source-to-binary correspondence has not been proved.

CURRENT RUNTIME

The released appliance later moved to a QEMU 10.2 stack incorporating Masayuki Murayama’s sun4v work. This page begins with the older QEMU 8.2.2 experiment.

04 / WHAT CAME NEXT

The lab became an appliance.

The next phase replaced the long-lived live session with an installed ZFS root, deterministic machine-description boot settings, native amd64 and arm64 builds, CI tests for boot and channel networking, and a public OCI image.
